# DDD design

## Compiler

* MKW-CS, 2021: Clang fork
* MKW-SP, 2021: GCC
* DDD, 2023: MWCC

Most GameCube and Wii games are compiled with MWCC which has its own C++ ABI.
This means that code generated by GCC and Clang (Itanium ABI) is not binary-compatible.
This is only an issue with C++, not with C.

Stock GCC or Clang can still be used in practice with the help of many fragile workarounds.
Complex cases like multiple inheritance or non-zero vtable offsets only make things worse.
Incorrect implementations of such workarounds are hard and often counterintuitive to debug.

There is a [Clang fork][] with MWCC compatibility patches as well.
As of 2021 it wasn't able to handle some more complex cases.
Regular rebases on top of the latest LLVM updates would be an additional maintenance burden.
This is also a barrier to new contributors as they would have to build LLVM or trust a prebuilt.

As there is a free version of MWCC, this became the preferred option.
It is however limited to C++03, has poor codegen, few parameters and its bugs will never be fixed.
It also needs a compatibility layer on non-Windows platforms.

## Launcher

* MKW-CS, 2021: Homebrew application
* MKW-CS, 2021: Riivolution
* MKW-SP, 2021: Riivolution
* MKW-SP, 2022: Homebrew application
* DDD, 2023: Homebrew application

We need a way to launch our mod on console and on Dolphin.
Since Dolphin made the SD card easier to use, Riivolution doesn't really make sense for complex mods.
If random numbers are generated with `/dev/es`, a Wii disc or a channel must be part of the boot chain.

## Patching system

* MKW-CS, 2021: `replacements.txt` and `removals.txt`
* MKW-CS, 2021: `REPLACE`
* MKW-SP, 2021: `PATCH_*`
* MKW-SP, 2022: `REPLACE`/`REPLACED` and `PATCH_*`
* DDD, 2023: `REPLACE`/`REPLACED`

We need a way to patch game functions while reusing them as well.
Assembly patches are error-prone, hard to understand and a pain to maintain.
`REPLACE`/`REPLACED` is battle-tested at this point.
One of its only limitations is that `REPLACED` cannot be used with constructors and destructors.

## Transport layer

* MKW-SP, 2022: TCP and UDP
* DDD, 2024: UDP

UDP is needed for anything real-time, thus it's simpler to use it for everything.
The stream-oriented aspect of TCP is not desirable when all other layers are message-oriented.

## Security layer

* MKW-SP, 2022: libhydrogen (Noise NK and XX)
* DDD, 2024: Noise IK

Noise IK does exactly what we want, is simple and well designed.
There are many implementations of the typical crypto primitives.
Something like DTLS would make it easier to update keys and to add post-quantum security.
However as of 2025 there are few good embedded DTLS libraries.

## Application layer

* MKW-SP, 2022: Protobuf
* DDD, 2024: ddd-formats

Protobuf is rather complex and not really designed to be used without heap allocation.
It also introduces extra tooling and noisy boilerplate.
On the other hand a custom system can be minimal.
The codegen can easily be tweaked to make it work well with C++03 for instance.

## Server location

The goal is to reduce latency for most players.

As [stebler][] decided to stick with OVH, the following sites were evaluated:

- **bhs**: Beauharnois, Canada (near Montreal)
- **eri**: Erith, UK (near London)
- **gra**: Gravelines, France (near Dunkirk)

The following tools were used to measure latency:

- <https://check-host.net/check-ping>
- <https://viewdns.info/ping>

| Location     | `bhs.lg.ovh.net` | `eri.lg.ovh.net` | `gra.lg.ovh.net` |
| :----------- | ---------------: | ---------------: | ---------------: |
| Atlanta      |        **24 ms** |            86 ms |            93 ms |
| Coventry     |            79 ms |         **4 ms** |             6 ms |
| Johannesburg |           253 ms |       **168 ms** |       **168 ms** |
| Mumbai       |           206 ms |       **136 ms** |       **136 ms** |
| São Paulo    |       **124 ms** |           198 ms |           194 ms |
| Seattle      |        **69 ms** |           141 ms |           148 ms |
| Sydney       |       **197 ms** |           267 ms |           272 ms |
| Tokyo        |       **171 ms** |           241 ms |           248 ms |
| Warsaw       |           107 ms |            32 ms |        **26 ms** |

The **Beauharnois** site was chosen as it seems to offer the best compromise.
In particular, the Seattle and Warsaw results motivated that decision.
